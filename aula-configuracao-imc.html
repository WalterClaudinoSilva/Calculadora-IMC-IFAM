Bem-vindos à Calculadora de IMC IFAM

Nesta jornada épica de 50 passos, nós vamos destrinchar cada milímetro do código que você usou para construir a Calculadora de IMC IFAM. Este não é um tutorial de "copiar e colar".

Quais são os nossos objetivos pedagógicos com este projeto?

  • Compreender a Arquitetura Android: Entender como o Front-end (XML visual) e o Back-end (Kotlin lógico) trabalham de forma separada, porém perfeitamente conectada.
  • Dominar o Design Responsivo: Aprender a criar interfaces poderosas com ConstraintLayout que se adaptam matematicamente a telas pequenas de celulares antigos ou a telas gigantes de tablets modernos, sem perder o alinhamento.
  • Lógica de Programação Segura: Desenvolver algoritmos que não apenas calculam o Índice de Massa Corporal (IMC) corretamente segundo a Organização Mundial da Saúde (OMS), mas que também "preveem" erros humanos (como clicar no botão sem digitar o peso). O aluno aprenderá a usar "Escudos" (try/catch) para evitar que o aplicativo feche bruscamente ("Crash").
  • Gerenciamento de Assets Visuais: Entender a diferença vital entre usar imagens fotográficas pesadas e criar elementos usando matemática pura através de vetores (SVG e Shapes), gerando um aplicativo levíssimo e sem perda de resolução.
  • Publicação Física (Deploy): Ao final do módulo, o aluno saberá como quebrar as travas de fabricante do seu celular Android habilitando o modo desenvolvedor e rodando seu próprio código fisicamente via cabo USB.

Aviso ao Aluno: Se você absorver os "porquês" por trás de cada linha explicada nesta documentação, você terá a base necessária para criar qualquer outro aplicativo de formulário no futuro.

O que é o Android Studio?

O Android Studio é a ferramenta de trabalho oficial criada pelo Google. Ele não é apenas um editor de textos; ele é classificado como uma IDE (Ambiente de Desenvolvimento Integrado). Mas o que isso significa na prática?

Significa que ele é um "canivete suíço" gigante que esconde a complexidade de criar um aplicativo. Se você não usasse o Android Studio, precisaria usar o bloco de notas para programar, abrir uma tela preta (terminal) para compilar, baixar arquivos zip do Google manualmente e enviar o app por cabo para o celular digitando comandos longos. A IDE faz tudo isso com um clique!

Os 4 Motores Internos do Android Studio:

  • Editor Inteligente (IntelliSense/Code Completion): Você não precisa decorar códigos difíceis. O Android Studio prevê o que você quer digitar. Se você começa a digitar Butt..., ele completa para Button e já importa os pacotes necessários de forma automática, apontando e corrigindo erros de sintaxe em tempo real antes mesmo de você salvar.
  • Emulador Integrado (AVD): Ele possui celulares e tablets "virtuais" (Android Virtual Device) rodando dentro da memória do seu computador. Isso permite testar o aplicativo simulando toques, rotação de tela, GPS e até fingindo receber mensagens, sem precisar de um aparelho físico.
  • O Dicionário SDK (Software Development Kit): O Android Studio baixa automaticamente as "regras de tradução" do Android. É o SDK que ensina ao seu computador, por exemplo, como a interface de uma câmera funciona no Android 14.
  • Design Visual (Layout Editor): Permite que você construa o visual do aplicativo arrastando botões e caixas de texto com o mouse, gerando o código XML automaticamente por baixo dos panos, e visualizando o design da tela em vários tamanhos de celulares diferentes simultaneamente.

O Paradigma Front-end vs Back-end

Diferente de sistemas web mais antigos ou pequenos scripts onde visual e lógica ficam embolados num único arquivo, o sistema Android força o desenvolvedor a usar uma arquitetura estritamente separada. Isso evita bagunça estrutural em projetos gigantes.

Pense na construção de um carro: uma equipe projeta a lataria, os bancos e a pintura (o visual e conforto), e outra equipe constrói o motor e a injeção eletrônica (a inteligência). No Android, funciona exatamente assim:

1. O Front-end: A Casca e o Design (Arquivos XML)

  • A Linguagem Passiva: Usamos arquivos com a extensão .xml (eXtensible Markup Language). A única responsabilidade do XML é ditar coordenadas para o celular: "Desenhe um retângulo verde aqui", "Coloque um texto azul ali".
  • A "Cegueira" do Front-end: Um arquivo XML é burro. Ele não "pensa". Se você construir um botão verde via XML, ele será lindo, mas você pode apertá-lo um milhão de vezes e absolutamente nada acontecerá. O XML não sabe fazer somas, multiplicar ou salvar arquivos. Ele apenas "veste o manequim" na vitrine.

2. O Back-end: O Motor e o Cérebro (Arquivos Kotlin)

  • A Inteligência Ativa: Usamos arquivos com a extensão .kt (Kotlin). Esta é uma linguagem de programação pesada, voltada para processamento de algoritmos e interação com a CPU do aparelho. O Kotlin não sabe desenhar botões bonitos. O mundo dele é pura matemática e lógica de processamento.
  • A Conexão (O Casamento Perfeito): O Kotlin funciona como o sistema nervoso central oculto atrás da tela do celular. Nós programamos o Kotlin para lançar "fios" até o XML e agarrar o botão visual. Instalamos ouvidos biônicos nesse botão (os chamados Listeners). A partir desse momento, quando o usuário aperta a tela (Front-end), o Kotlin (Back-end) escuta o clique instantaneamente, captura as palavras digitadas, processa a matemática do IMC e injeta a resposta de volta no XML, alterando o texto que o usuário vê!

A Estrutura de Pastas: A Tríade do Android

app/
├── manifests/
│   └── AndroidManifest.xml
├── java/
│   └── br.com.roboticminds.calculadoradeimc_ifam
│       └── MainActivity.kt
└── res/
    ├── drawable/  (Imagens e Vetores)
    ├── font/      (Tipografia)
    ├── layout/    (Telas XML)
    ├── mipmap/    (Ícones do App)
    └── values/    (Cores e Textos globais)

Você tem razão sobre a deformidade! Sem a tag especial <pre>, o navegador "esmagava" os espaços do desenho. Agora a árvore está preservada. Quando você cria um projeto no Android Studio, ele gera dezenas de pastas automáticas. Mas para programar de verdade, focamos 100% da nossa energia em apenas três lugares essenciais. É a "Tríade de Ouro" do Android:

1. Manifests (O Passaporte de Identidade)

O arquivo AndroidManifest.xml é o documento mais importante para o Sistema Operacional do celular. Antes do Android permitir a instalação do app, ele lê este arquivo de cima a baixo. É aqui que declaramos o nome do aplicativo, qual é o ícone oficial que vai pra tela do celular e qual tela deve ser carregada primeiro quando o usuário clicar no ícone. Mais importante ainda: é no Manifest que pedimos Permissões. Se o seu app precisar usar a Câmera ou a Internet, e você não declarar uma tag de permissão aqui, o Android (Google) bloqueia o acesso de forma implacável por segurança.

2. Java (O Cofre do Cérebro)

Apesar do nome da pasta ser "java" por uma questão histórica de engenharia reversa do Google, é aqui dentro que moram todos os nossos modernos arquivos Kotlin (.kt). Todo o sistema nervoso, o "Back-end", a matemática da divisão por 100 e a inteligência lógica que programamos ficam seguramente organizados dentro do nosso Package (que é como se fosse o nosso CEP na loja de aplicativos da Play Store).

3. Res (O Guarda-Roupa Visual)

A palavra "Res" é o apelido carinhoso para Resources (Recursos). Absolutamente tudo que é arte, design e enfeite fica restrito a esta pasta. A organização é levada a níveis militares:

  • drawable/: Guarda arte pura (Formas, cores sólidas, vetores SVG e imagens de logo).
  • layout/: É a prancheta de desenho das Telas. O famoso arquivo visual activity_main.xml mora aqui.
  • mipmap/: Esta pasta é "blindada" e serve exclusivamente para abrigar os ícones do aplicativo que vão para a tela inicial do aparelho do usuário (Launcher icons). Ela entrega resoluções variadas para que o ícone nunca fique embaçado.
  • values/: Uma pasta genial para variáveis de design (como colors.xml e strings.xml). Se você pintar 50 telas diferentes do app de "Verde IFAM" e amanhã o instituto mudar o logo para Azul, você NÃO precisa abrir as 50 telas para alterar a cor. Você abre a pasta values, altera o código hexadecimal lá, e as 50 telas ficam azuis em 1 segundo. Isso é arquitetura profissional!

O Gradle

Você com certeza já notou uma barrinha verde demorando para carregar na parte inferior do Android Studio escrito "Gradle Build Running". Mas o que exatamente ele está fazendo?

Se o Android Studio fosse uma fábrica de automóveis, o Gradle seria a linha de montagem e o engenheiro-chefe. Ele é um sistema avançado de automação de construção (Build Automation Tool).

O que o Gradle faz na prática?

  • O Coletor de Bibliotecas: O Gradle viaja até os servidores na internet em milissegundos e baixa automaticamente códigos prontos do Google ou de terceiros (como bibliotecas gráficas ou de internet) que você declara no arquivo build.gradle.kts. Você não precisa baixar e instalar arquivos ".zip" manualmente.
  • O Compilador Criptografado: O celular não consegue ler o idioma "Kotlin" puramente humano que você escreveu. O Gradle traduz o seu código para uma linguagem bruta de máquina (Bytecode), hiper-rápida, que o processador do smartphone consegue executar de forma instantânea.
  • O Empacotador (Packager): O celular não roda pastas soltas. O Gradle junta toda a lógica matemática compilada, compacta todas as imagens da pasta res, insere a identidade do Manifest, e funde tudo isso num único bloco de software blindado.

A Geração do Produto Final (APK)

O resultado que o Gradle ejeta no final desta pesada linha de montagem é o aplicativo de fato: um arquivo de formato .APK (Android Package Kit) ou .AAB (Android App Bundle). É este pacote assinado digitalmente pelo Gradle que nós enviamos para a Google Play Store para ser distribuído ao mundo inteiro.

Aviso ao Aluno: Seu projeto Android sempre terá dois arquivos Gradle. Um de Nível de Projeto (controla configurações globais) e um de Nível de Módulo (onde definimos regras específicas, como a versão mínima do Android que nosso app aceita).

A Pasta Drawable: Bitmap vs Vetor

Dentro da pasta res/drawable/ nós alocamos os recursos visuais brutos do aplicativo. Mas aqui existe um segredo de ouro do desenvolvimento mobile: A Guerra entre Bitmaps e Vetores.

Se você colocar um arquivo .jpg ou .png (Bitmaps) lá dentro, ele terá um tamanho físico fixo (ex: 500x500 pixels). Se um usuário abrir o seu app num tablet de 12 polegadas, o Android terá que esticar essa imagem. O resultado? Uma imagem feia, borrada e "pixelada". Além disso, imagens fotográficas deixam o arquivo do aplicativo extremamente pesado (GigaBytes).

A solução moderna? Vetores (Arquivos XML). Em vez de desenhar os pixels, nós damos uma equação matemática para o processador do celular. A CPU calcula e desenha a forma em tempo real na tela. Se você esticar um Vetor para o tamanho do planeta Terra, ele terá a qualidade gráfica perfeita, pois matemática não perde resolução!

Dissecando o background.xml (A Forma)

<?xml version="1.0" encoding="utf-8"?>
<shape xmlns:android="http://schemas.android.com/apk/res/android"
    android:shape="rectangle">

Vamos analisar a criação do nosso fundo verde linha a linha:

<?xml version="1.0"...?>: A assinatura obrigatória. Avisa ao celular que este arquivo segue as regras de estruturação XML universais na codificação UTF-8 (que aceita acentos).
<shape ...>: Abre a tag de "Forma". Isso diz ao Android Studio que nós não queremos uma foto, nós queremos gerar uma forma geométrica matemática.
xmlns:android="...": Define o dicionário de palavras. Ensina ao arquivo o que a palavra "android" significa, importando os esquemas oficiais do Google.
android:shape="rectangle": O comando mestre. Pede ao processador gráfico para desenhar um Retângulo perfeito que, por padrão, tentará preencher todo o espaço onde for invocado.

Dissecando o background.xml (O Gradiente)

    <gradient
        android:angle="175"
        android:startColor="@color/ifam_green_light"
        android:endColor="@color/ifam_green_dark"
        android:type="linear"/>
</shape>

Um retângulo transparente não serve para nada. Precisamos pintá-lo internamente usando a tag <gradient>:

android:type="linear": Define que a transição de cores será uma linha reta (não será um círculo do centro para as bordas, como no tipo "radial").
android:startColor="@color/ifam_green_light": A cor inicial. O código HEX #98c29c representa o exato tom de verde-claro institucional que nós escolhemos.
android:endColor="@color/ifam_green_dark": A cor final. É o verde institucional profundo e mais escuro. O celular fará a transição suave de uma para a outra.
android:angle="175": O toque de Mestre! Em vez de a cor ir da esquerda (0º) para a direita, ou de baixo para cima (90º), nós giramos a pintura em exatos 175 graus. Isso cria aquele efeito de inclinação super moderno e dinâmico que os grandes apps usam hoje em dia.

Vetores Matemáticos (wave.xml)

<vector xmlns:android="http://schemas.android.com/apk/res/android"
    android:width="1440dp"
    android:height="320dp"
    android:viewportWidth="1440"
    android:viewportHeight="320">

Lembra da forma de Trapézio (antiga onda) no rodapé do nosso projeto? Ela é gerada pelo wave.xml usando a poderosa tag <vector> (O equivalente Android para arquivos SVG).

width e height: Definem o tamanho "sugerido" do vetor na tela (ex: 1440dp). Mas a mágica está nas linhas de baixo.
viewportWidth e viewportHeight: Este é o segredo! Eles criam uma "lousa matemática virtual" interna. Nós dissemos ao Android: "Crie uma lousa mental de 1440 por 320 pedaços". O desenho do trapézio será feito exatamente dentro dessa lousa. Se a tela do usuário tiver apenas 400 pixels de largura, o Android encolhe toda a lousa mantendo a proporção matemática perfeita da forma.

Dissecando o Trapézio (O atributo Path)

  <path
      android:pathData="M0,160L60,170.7C120,181,240...Z"
      android:fillColor="@color/ifam_green_dark"/>
</vector>

Se você abrir o wave.xml verá um bloco de letras e números bizarros. Isto é a linguagem universal de Geometria de Vetores (Path Data):

M (Move To): M0,240 significa "Levante a caneta e coloque-a na coordenada X=0 e Y=240 daquela nossa lousa mental (Começando o lado esquerdo mais baixo/curto)".
L (Line To): L1440,80 significa "Faça um risco perfeitamente reto em diagonal até o lado direito na altura 80 (Deixando o lado direito mais alto/comprido)".
L (Line To): Os próximos passos (L1440,320 e L0,320) desenham as linhas retas até a base do retângulo da tela. Graças a isso, não precisamos de um arquivo de imagem pesado para termos um enfeite poligonal no rodapé!
Z e fillColor: O "Z" fecha o polígono conectando o último ponto ao primeiro. Após a caneta terminar, o celular "derrama" (fill) a cor definida dentro das linhas fechadas.

O Desafio do Bitmap (logo.png)

O nosso arquivo logo.png também reside na pasta drawable. Apesar do que falamos no Slide 6, desenhar um logotipo complexo usando pura matemática de vetores (Path Data) às vezes é difícil demais ou consome muito processamento. Por isso, ainda usamos imagens PNG (Bitmaps) para logotipos fotográficos ou muito complexos.

A Armadilha das Densidades (DPI)

Se você colocar um logo pequeno de 100x100 pixels, ele ficará lindo em um celular antigo. Mas se um usuário baixar seu app num moderno Galaxy S24 Ultra (que possui uma tela "Quad-HD" super adensada), os 100 pixels originais vão ser esticados pelo sistema para preencher o espaço físico da tela. O logo ficará completamente embaçado (borrado).

A Solução Profissional: Em projetos reais, nós não temos apenas uma pasta drawable. Nós teríamos pastas como drawable-mdpi, drawable-hdpi, drawable-xhdpi, e colocaríamos tamanhos diferentes do mesmo logo (pequeno, médio, gigante) em cada uma delas. O Android é inteligente o suficiente para descobrir qual a potência da tela do usuário e puxar magicamente a imagem da pasta correta!

Você reparou que nós criamos uma pasta res/font/ e colocamos um XML chamado afacad.xml lá dentro?

Dessa forma, nosso App não engorda o celular do usuário e mantém uma estética lindíssima baseada no catálogo gratuito do Google Fonts!

Como importar a Fonte na Prática

A teoria das fontes (Slide 12) é linda, mas como fazemos na prática?

O que é o ConstraintLayout?

Antes de olharmos o código da tela, precisamos entender a "Prancheta" onde estamos desenhando: o famigerado ConstraintLayout.

A Evolução: Antigamente, criar telas no Android exigia empilhar caixas dentro de caixas (Linear Layouts). Se você quisesse um botão do lado de um texto, precisava criar uma caixa invisível só para segurá-los. Isso deixava o celular lento para processar tantas caixas aninhadas.
O Quadro Magnético: O ConstraintLayout é completamente "plano" (Flat). Você joga todos os botões e textos soltos na tela e os amarra usando regras magnéticas bidirecionais (elásticos visuais). Exemplo: "Prenda a base do botão X no teto do botão Y".
A Vantagem Extrema: Se a tela for de um relógio apertado ou de uma TV esticada, as amarras (constraints) encolhem ou expandem de forma perfeitamente simétrica, mantendo o seu design responsivo sem precisar que você programe resoluções diferentes!
